# Intervention Evidence Layer

Status: active design artifact.

Last updated: June 6, 2026.

See [glossary.md](glossary.md) for the canonical definitions of donor,
recipient, site, target, runtime hook, operator, schedule, outcome, control,
trial, run, sweep, study, and mechanism card.

## Focus

VLA Lens needs one focused layer that makes this workflow executable:

```text
episode behavior
  + discovery artifact
  -> intervention target
  -> intervention run
  -> action or rollout outcome
  -> inspectable evidence
```

This is not a request for a giant intervention taxonomy, a new capture profile,
or a separate planning product. The first useful layer should let a researcher
take an existing episode and an existing artifact, intervene on the candidate
signal, measure what changed, and save a lossless record of the result.

The core product object is:

```text
InterventionRun = exact executed spec + outputs + outcome metrics + provenance
```

V0 stores this through a workbench `intervention_record`. That shell type is
not a causal-evidence claim. Causal interpretation comes from the record
contents: status, trials, outcomes, controls, claim labels, runtime/preflight
state, and provenance.

For v0, a separate `InterventionPlan` object is not required. The saved run
must contain the full recipe that was executed, so future code can inspect,
rerun, aggregate, or promote the result without guessing what happened.

## Product Loop

The intended research loop is:

```text
1. Open an episode or cohort.
2. Inspect a discovery artifact: probe, contrast direction, attention map,
   action-generation artifact, cluster, or manual model-site selection.
3. Convert the artifact into a target.
4. Choose an intervention operator.
5. Run a fast policy-call counterfactual when runtime support is available.
6. Compare original, no-op, and intervened action outputs.
7. Save an InterventionRun as a LensArtifact.
8. Optionally scale the same saved spec to more trials, controls, or cohorts.
```

The UI action that ties this together should be researcher-facing:

```text
Intervene with this signal
```

or:

```text
Send to Intervention
```

The backend can store precise target, operator, schedule, outcome, and
provenance fields. The UI does not need to expose those names first.

## V0 Non-Goals

Do not make the first implementation depend on these:

```text
- new PI0.5 capture profiles
- full closed-loop rollout
- SAE or transcoder support
- a separate queued-job planning system
- automated claim grading
- high-powered statistics before a single run works
- changing PolicyCallRecord unless a concrete missing field is proven
```

Existing captures should remain valid. A capture may be viewable even when live
rerun is unavailable. Runtime support should be capability-gated and checked by
preflight, not assumed from the mere presence of policy-call rows.

## V0 Acceptance Split

The first implementation has two separate milestones:

```text
Evidence Layer v0:
  saved, listable, inspectable intervention_record payloads.
  These records must open in the normal dashboard environment without PI0.5,
  Torch, LeRobot, LIBERO, GPU dependencies, or model checkpoints.

Runtime v0:
  live PI0.5 direction intervention execution.
  This comes later, behind preflight and the dedicated PI0.5 runtime
  environment.
```

## Conceptual Layers

The full idea should be preserved losslessly, but the implementation should
enter through the smallest useful slice.

```text
Context:
  where the behavior happened

Discovery:
  what internal signal might matter

Target:
  the exact internal object to manipulate

Intervention:
  the operation applied to the target

Outcome:
  what changed

Control:
  whether the effect was specific

Evidence:
  the saved record and claim context
```

This layer should not collapse those concepts into one vague blob. It should
also not require every concept to be implemented at once.

## Context

Context objects answer: where are we in the robot/model trace?

```text
Episode:
  one robot trajectory or rollout.

PolicyCall:
  one model invocation aligned to an episode timestep.

Observation:
  the model input at a policy call.

ActionChunk:
  the action sequence generated by one policy call.

ModelSite:
  a named captured model tensor location.

TokenSpace:
  language, image, action, expert, or model-specific token axis.

Cohort:
  selected set of episodes, timesteps, policy calls, or artifact examples.
```

V0 should treat `PolicyCall` as the stable address of a model invocation, not as
the place to stuff every possible rerun detail. Rerun readiness should be
derived from existing dataset tables, manifest metadata, model adapter metadata,
and runtime preflight checks.

## Discovery Artifacts

Discovery artifacts answer: what internal signal might matter?

Examples:

```text
Probe:
  supervised readout from activations to a behavior, label, phase, or outcome.

MeanDifferenceDirection:
  contrast direction between two groups, such as close vs open.

ActionGenerationArtifact:
  saved summary of how action chunks form over generation steps.

AttentionOrAttributionMap:
  localization clue over tokens, patches, heads, or sites.

ActivationCluster:
  group of similar model states or robot moments.

ManualSelection:
  researcher-chosen site, token, feature, layer, call, or timestep.

SAEFeature / TranscoderFeature / CrosscoderFeature:
  future sparse or pathway candidates, not v0 requirements.
```

Discovery artifacts create candidates. They do not prove causality by
themselves.

## TargetSpec

`TargetSpec` is the bridge between discovery artifacts and intervention
execution.

```text
TargetSpec =
  source artifact or manual selection
  + model/site identity
  + tensor axes and selectors
  + representation to manipulate
```

Representative fields:

```text
kind:
  probe_direction | contrast_direction | activation_slice | feature |
  subspace | head | edge | manual

source_artifact_id:
  artifact that produced the candidate, if any

model_site:
  captured model-site name or site id

token_space:
  action | image | language | expert | model-specific

token_selector:
  all action tokens, token index, object-region image tokens, etc.

reduction:
  mean, none, flat, first token, horizon slice, etc.

representation:
  vector, feature index, subspace basis, activation slice, patch source
```

Important distinction:

```text
ModelSite:
  where a tensor is captured or named in the overlay.

TargetSpec:
  the selected object inside that site that will be manipulated.

Runtime hook:
  the adapter-specific live model boundary where the operation is applied.
```

The runtime hook does not need to be a first-class research object in v0. The
model adapter can resolve a target to a hook internally. But the saved run
should record enough information to see which target was intended and which
runtime hook was actually used.

## InterventionSpec

`InterventionSpec` records what operation was applied.

Representative fields:

```text
operator:
  add_direction | project_out_direction | replace | ablate | clamp |
  source_patch | mean_replace

strength:
  scalar strength or named sweep value

schedule:
  when the operation was active

parameters:
  operator-specific settings

controls:
  optional no-op, random direction, wrong layer, wrong time, wrong token,
  shuffled donor, or matched baseline references
```

V0 should focus on:

```text
AddDirection
ProjectOutDirection
NoopRerun
RandomDirectionControl
WrongLayerControl, if easy for PI0.5
```

Source patching, feature clamps, attention patching, and path patching can be
added later without changing the conceptual layer.

## Schedule

Interventions are temporal. A target and operator are incomplete without an
answer to when the operation was active.

Representative fields:

```text
policy_call:
  one call or a set/range of calls

timestep:
  optional environment timestep range

generation_step:
  optional action-generation or flow step range

action_horizon:
  optional future action positions affected or measured

token_selector:
  optional schedule over selected tokens
```

V0 can start with one selected policy call. The schema should still leave room
for generation-step and horizon schedules because PI0.5-style action formation
uses those axes.

## OutcomeSpec

`OutcomeSpec` records what was measured.

The privileged first outcome is:

```text
ActionOutcome
```

Representative fields:

```text
stored_original_action:
  action chunk already saved in the dataset

noop_action:
  regenerated action chunk without intervention, if runtime rerun is available

intervened_action:
  regenerated action chunk under intervention

delta:
  intervened minus no-op, and optionally intervened minus stored original

action_basis:
  raw, gripper, eef_delta_xyz, rotation, speed, object-relative,
  task-relative, pca, or learned action feature

horizon:
  which action horizon positions were compared

metrics:
  raw delta, normalized delta, side-effect score, specificity summaries
```

Action-basis interpretation must be explicit. A resolved named basis should
record:

```text
action_schema_ref
basis_resolution
units
sign_convention
source_dimensions
normalization
```

If that metadata is unavailable, the result should stay in the raw basis or
return partial basis resolution. Do not silently infer gripper, xyz, rotation,
or task-relative dimensions.

Rollout outcomes are future-strengthening evidence, not required for the first
usable product slice.

```text
RolloutOutcome:
  success, final distance, contact, collision, trajectory, video, reward

TokenOutcome:
  text/logit/image-token result for VLM-style tests

ProbeOutcome:
  before/after probe score
```

## No-Op And Repeated Trials

For v0, saving one no-op rerun is enough when runtime rerun is available:

```text
stored original
noop regenerated
intervened regenerated
```

The format must not assume only one trial forever. It should allow repeated
trials and later aggregation:

```text
InterventionRun:
  trials: [trial_0, trial_1, ...]

InterventionSweep:
  repeated runs over strength, layer, time, target, or seed

InterventionStudy:
  sweeps plus controls across a cohort
```

This lets the first implementation stay simple while leaving room for better
statistics later.

## Runtime Preflight

Runtime preflight answers: can this requested intervention actually run here?

It should check for capabilities such as:

```text
reconstructable_policy_call:
  can the selected model input be rebuilt from saved dataset state?

model_runtime_available:
  can the model adapter load the requested model/checkpoint?

target_resolvable:
  can the TargetSpec be mapped to a runtime hook?

action_decoder_available:
  can model output be decoded into comparable action chunks?

action_basis_available:
  can raw actions be converted into requested action bases?

runtime_environment_safe:
  is the requested work using the dedicated PI0.5 capture/runtime environment
  when model execution requires PI0.5/LeRobot/LIBERO dependencies?
```

This preflight is not a requirement to change capture profiles. If a dataset is
missing runtime details, the UI should say the intervention can be inspected but
not rerun from this root.

## Evidence Objects

Saved evidence should remain compatible with the existing `LensArtifact`
provenance shell. The typed intervention object defines meaning; `LensArtifact`
handles durable artifact indexing and array references.

Recommended artifact types:

```text
intervention_run:
  one target, operator, context, outcome, and provenance record

intervention_sweep:
  multiple related intervention runs over strength, layer, call, token, or time

intervention_study:
  sweep plus controls over a cohort

mechanism_card:
  human-readable claim assembled from multiple artifacts
```

`InterventionRun` should contain:

```text
run_id
title
schema_version
status
created_utc

identity:
  dataset_id or dataset_root_id, dataset_fingerprint, trace_id,
  policy_call_index, and source_artifact_id when artifact-derived

context:
  dataset root identity, trace_id, episode_id, policy_call_index,
  timestep/frame, instruction/task, selected preview media

target:
  TargetSpec

intervention:
  InterventionSpec

outcome:
  OutcomeSpec plus measured results

controls:
  control run references and metrics, if any

runtime:
  preflight result, model adapter, hook resolution, action decoder,
  execution environment, error/warning details

provenance:
  source artifacts, source traces, code version, dataset fingerprint,
  model identity, created_utc
```

## Claim Language

The UI should avoid treating all artifacts as equally strong.

Research-facing labels can be:

```text
Observation:
  interesting example, activation, attention, or cluster pattern

Predictive:
  heldout probe or association evidence

Causal-local:
  intervention changes one policy-call output

Causal-cohort:
  effect holds over a cohort

Behavioral:
  rollout-level behavior changes

Specific:
  controls reduce the chance that this is generic model damage
```

These labels should be mapped to existing guardrail vocabulary instead of
forking a second trust system:

```text
integration_smoke:
  observation or plumbing evidence

decodable:
  predictive evidence

candidate_mechanism:
  predictive evidence plus localized target and planned controls

causal_intervention:
  intervention artifacts, replay/no-op checks, controls, and behavior/effect
  evidence
```

V0 does not need automated claim grading. It should store enough fields that
later guardrails can classify or reject overclaims.

## Minimal Product Slice

The first concrete implementation should be:

```text
Probe Direction Intervention v0
```

Input:

```text
probe artifact
selected episode
selected policy call
selected model site
strength or strength sweep
action basis request
```

Operation:

```text
AddDirection
ProjectOutDirection
```

Outcome:

```text
stored original action chunk
noop regenerated action chunk, if available
intervened action chunk
raw action delta
gripper / xyz / rotation deltas when basis metadata exists
```

Controls:

```text
noop rerun
random direction
wrong layer, if the adapter can resolve it cheaply
```

Output:

```text
LensArtifact(type="intervention_run")
arrays for action chunks and deltas
display metadata for an Intervention Card
saved workbench/intervention run row
```

The first UI affordance should appear on probe and episode/artifact surfaces:

```text
Intervene with this signal
```

## API Sketch

The future live-run API can look like this, but v0 may also begin with saved
records only:

```json
{
  "trace_id": "episode_000042",
  "policy_call_index": 7,
  "target": {
    "kind": "probe_direction",
    "source_artifact_id": "probe-gripper-close-v1",
    "model_site": "pi05.expert.layers.12.hidden_tokens",
    "token_space": "action",
    "reduction": "mean"
  },
  "intervention": {
    "operator": "add_direction",
    "strengths": [-3, -1, 0, 1, 3],
    "schedule": {
      "policy_calls": [7],
      "generation_steps": "all",
      "tokens": "action"
    }
  },
  "outcome": {
    "kind": "action",
    "basis": ["raw", "gripper", "eef_delta_xyz"],
    "horizon": "full_chunk"
  },
  "controls": [
    {"kind": "noop_rerun"},
    {"kind": "random_direction"},
    {"kind": "wrong_layer"}
  ]
}
```

The saved result should include the exact request-like payload that produced it,
not only summary metrics.

## Why This Layer Matters

This layer makes failure informative.

Examples:

```text
Probe predicts action but steering does nothing:
  likely readout-correlated rather than causally used, or target/hook mismatch.

Intervention changes every action dimension:
  likely nonspecific or off-manifold.

Effect appears only at one layer/time:
  possible localized mechanism.

Effect appears on train but not heldout:
  discovery artifact may not generalize.

Action chunk changes but rollout does not:
  action effect may be too small, badly timed, or compensated by the environment.
```

The goal is not to guarantee clean mechanisms. The goal is to make candidate
signals testable and to save enough evidence that later research claims are
auditable.

## Implementation Order

Use the repository-root
`vla_lens_intervention_implementation_plan.md` as the Goal Mode runbook. Each
implementation phase has explicit scope, acceptance criteria, and verification
commands so the user can run:

```text
/goal implement Phase X
```

1. Add typed docs and glossary for the layer. This file is that artifact.
2. Add core dataclasses for `TargetSpec`, `InterventionSpec`, `OutcomeSpec`,
   and typed `InterventionRun` payloads.
3. Add serialization tests that save/load an `intervention_run` LensArtifact
   without model execution.
4. Add dashboard/API support for viewing saved intervention runs.
5. Add PI0.5 runtime preflight that reports why a selected policy call can or
   cannot be rerun.
6. Add one PI0.5 direction intervention runtime path.
7. Add action-basis adapters and no-op/control trials.
8. Add sweeps, cohort scaling, and stronger guardrails.

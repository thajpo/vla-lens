## Main Question

PI0.5 sometimes knows about the requested object but still acts toward a different object.

The project is now about that gap:

> When the instruction names an object, does that object keep control of the robot's action?

We track this chain:

```text
requested object
object suggested inside the model
object suggested by the action
first object moved
first object lifted
```

## The Big Warning

Task ID, layout, and object positions explain a lot.

That means a simple prediction test can look impressive while mostly rediscovering easy shortcuts.

Rule:

> Do not treat a saved model state as meaningful unless it beats the best task/layout shortcut on held-out layouts.

## What Passed The Strict Check

Saved hidden states could predict which object would be moved or lifted better than task/layout shortcuts.

They did not cleanly predict broad success or failure type.

| saved feature | first moved object | first lifted object | success | failure type |
|---|---:|---:|---:|---:|
| vision/language hidden state | pass | pass | fail | fail |
| middle/prefix hidden state | pass | pass | fail | fail |
| action-expert hidden state | pass | pass | fail | fail |
| pooled final action chunk | fail | fail | fail | fail |
| pooled final action-generation state | fail | fail | fail | fail |

Plain meaning:

> The saved hidden states contain information about which object the robot will interact with. But broad success/failure remains mostly explained by task and layout.

## Why Broad Success Is Not Enough

A rollout can fail for many reasons:

- it moved the wrong object
- it lifted the wrong object
- it approached the right object but missed
- it got close but closed the gripper badly
- it lifted the target but failed later

These are different problems.

The cleanest current problem class is:

```text
requested object != object the robot moves or lifts
```

## Action-Direction Findings

We compared the direction of the generated action with directions to objects in the scene.

Main result:

- approach failures are often still aimed near the target
- wrong-object moved/lifted failures often point more toward a distractor than the target

| failure type | rollouts | median target-vs-distractor margin | target wins rate |
|---|---:|---:|---:|
| approach failure | 99 | 0.2498 | 0.7174 |
| close but far from target | 70 | -0.2139 | 0.3476 |
| wrong object lifted | 285 | -0.2154 | 0.2915 |
| wrong object moved | 78 | -0.2752 | 0.2463 |

Plain meaning:

> Wrong-object moved/lifted failures are the best place to study how the robot chooses the wrong object. Approach failures may be more about control or timing.

## Scene 3 Task 59

Scene 3/task 59 is still the clearest story:

```text
requested object: tomato_sauce_1
common wrong object: ketchup_1
often lifted object: alphabet_soup_1
```

But it has no clean good examples in the current captures.

There are `10` successful rollouts for the same requested object, but all are messy in some way.

Plain meaning:

> Scene 3/task 59 is good for understanding a failure. It is not yet good for showing that we can rescue the failure.

## Safe Claims

- The model often stores information related to which object will be moved or lifted.
- Wrong-object failures are repeatable enough to study directly.
- Task, layout, and object position must be controlled.
- Scene 4 is currently the best place to try a first model-change test.
- Scene 3/task 59 needs new clean good examples before rescue claims are fair.

## Claims We Have Not Earned

- We have not shown that changing a saved internal state changes the robot's object choice.
- We have not found the exact mechanism.
- We have not shown that repeated wrong objects are meaning mistakes.
- We have not shown that swapping a broad middle model state explains the failure.
- We have not shown that full task success can be rescued.

## Current Next Step

Before running a model-change test:

- fix the wrong-time control so it really uses a different time step
- reproduce saved actions from saved arrays with a fresh no-training model run
- start with one Scene 4 family
- measure whether the action shifts toward the requested object before measuring full task success
